# Admin Panel

Рабочий прототип сервиса с 3 уровнями профилей, заказами и оплатой заказов.

### Учётные данные

| Роль | Логин | Пароль |
|------|-------|--------|
| Админ | admin | admin123 |
| Profile+ | plus1@example.com | plus123 |
| Profile | std1@example.com | std123 |
| ProfileMin | min1@example.com | min123 |

---

## 1. Бизнес-логика

### Роли в системе

В системе два типа ролей:

1. **Администратор** — управляет всеми профилями и заказами, имеет полный доступ.
2. **Пользователь (профиль)** — Имеет один из трёх уровней: Profile+, Profile, ProfileMin.

### Иерархия профилей

Пользователи (профили) организованы в трёхуровневую иерархию:

```
Profile+ (верхний уровень)
  ├── Заказы
  └── Profile (дочерний профиль)
        ├── Заказы
        └── ProfileMin (дочерний профиль нижнего уровня)
              └── Заказы
```

- **Profile+** — верхний уровень. Не имеет родителя. Может содержать дочерние Profile.
- **Profile** — средний уровень. Родитель — Profile+. Может содержать дочерние ProfileMin.
- **ProfileMin** — нижний уровень. Родитель — Profile. Не может иметь дочерних профилей.

Каждый профиль имеет: имя, email, пароль, комиссию (%) и срок оплаты.

### Авторизация

Единая точка входа для всех пользователей — страница логина. Войти можно по email или имени + пароль.

### Права доступа

| Роль | Видит | Может создавать |
|------|-------|----------------|
| Админ | Все профили, все заказы | Профили любого типа, заказы |
| Profile+ | Себя, своих Profile, их ProfileMin | Profile под собой, заказы |
| Profile | Себя, своих ProfileMin | ProfileMin под собой, заказы |
| ProfileMin | Только себя и свои заказы | Заказы |

### Страницы и функциональность

- **Логин** — вход по email/имени + пароль
- **Profile+** — таблица всех Profile+ с агрегатами (кол-во заказов, суммы, суб-аккаунты)
- **Profile** — таблица всех Profile с указанием родителя и комиссии от родителя
- **ProfileMin** — таблица всех ProfileMin с указанием родителя и комиссии от родителя
- **Детали профиля** — полная информация: статистика, суб-аккаунты, заказы с инлайн-оплатой
- **Создание профиля / заказа** — формы (доступны по правам роли)

### Комиссия

У каждого профиля есть поле «комиссия» (%). У дочерних профилей на странице деталей и в таблицах отображается также «комиссия от родителя».

### Заказы

Каждый профиль (любого уровня) может иметь заказы. Заказ содержит: номер, сумму и оплаченную часть. Статусы:
- **Не оплачено** — оплата = 0
- **Частично оплачено** — оплата > 0, но меньше суммы
- **Оплачено** — оплата >= суммы

Оплата вносится с помощью кнопки «Оплатить» в карточке профиля.

### Агрегаты в таблицах

Для каждого профиля в таблице отображаются:
- Количество заказов
- Общая сумма заказов
- Оплачено
- Остаток (сумма − оплачено)
- Количество суб-аккаунтов (для Profile+ и Profile)

## 2. Открытые вопросы

### 1. Комиссия — влияние на заказы

**Текущая реализация:** комиссия хранится как процент в профиле и отображается в карточке/таблице. У дочерних профилей показывается «комиссия от родителя». На расчёты заказов комиссия **не влияет**.

**Вопрос:** должна ли комиссия автоматически применяться к заказам? Например:
- Вычитаться из суммы заказа при создании?
- Начисляться родительскому профилю как доход?
- Влиять на поле Сумма или отображаться отдельным полем в заказе?

### 2. Личный кабинет профиля — оплата заказов

**Текущая реализация:** профили могут авторизоваться в системе и видят свой кабинет с заказами. Кнопка «Оплатить» доступна всем — и админу, и самому профилю.

**Вопрос:** корректно ли это? Возможные варианты:
- Только админ может вносить оплату (профиль видит заказы в режиме «только чтение»)
- Профиль может сам оплачивать свои заказы (текущее поведение)
- Личный кабинет профиля не нужен вообще — только админ работает в системе

### 3. Срок оплаты — профиль или заказ

**Текущая реализация:** поле срок оплаты находится в профиле. У заказа срока оплаты нет.

**Вопрос:** где должен быть срок оплаты?
- В профиле — как общий дедлайн для всех заказов профиля (текущее поведение)
- В заказе — индивидуальный срок для каждого заказа
- В обоих местах — профиль задаёт дефолт, заказ может переопределить

### 4. Каскадное удаление профилей

**Текущая реализация:** при удалении профиля удаляются все его дочерние профили и все заказы по всей цепочке. Например, удаление Profile+ удалит все его Profile, их ProfileMin и все заказы на всех уровнях.

**Вопрос:** корректно ли каскадное удаление? Возможные варианты:
- Удалять всё каскадно (текущее поведение)
- Запретить удаление, если есть дочерние профили или заказы
- Отвязать дочерние профили (сделать их «системными», без родителя) вместо удаления

## 3. Техническая реализация

### Стек

- **Backend:** Go (Chi, GORM, JWT, bcrypt)
- **Frontend:** Vue 3, TypeScript, Tailwind CSS, shadcn-vue (dark theme)
- **БД:** PostgreSQL 16
- **Инфра:** Docker Compose

### Запуск

```bash
docker compose up --build
```

Приложение доступно на `http://localhost:3000`

### Архитектура БД

Все типы профилей хранятся в единой таблице `profiles` с дискриминатором `type` (`plus` / `standard` / `min`). Self-referencing `parent_id` строит дерево иерархии.

#### Таблица `profiles`

| Поле | Тип | Описание |
|------|-----|----------|
| id | uint, PK | Автоинкремент |
| type | string, NOT NULL | Тип профиля: `plus`, `standard`, `min` |
| parent_id | uint, FK, NULL | Ссылка на родительский профиль |
| name | string, NOT NULL | Имя профиля |
| email | string, UNIQUE | Email (используется для логина) |
| password_hash | string, NOT NULL | bcrypt хеш пароля |
| commission | float64 | Комиссия (%), по умолчанию 0 |
| payment_deadline | timestamp, NULL | Срок оплаты |
| created_at | timestamp | Дата создания |

Вычисляемые поля (не хранятся в БД, загружаются отдельным SQL-запросом): `total_amount`, `total_paid`, `total_remaining`, `order_count`, `sub_account_count`.

#### Таблица `orders`

| Поле | Тип | Описание |
|------|-----|----------|
| id | uint, PK | Автоинкремент |
| profile_id | uint, FK, NOT NULL | Ссылка на профиль-владелец |
| number | string, NOT NULL | Номер заказа |
| amount | float64, NOT NULL | Сумма заказа |
| paid | float64 | Оплачено, по умолчанию 0 |
| created_at | timestamp | Дата создания |

Вычисляемые поля (не хранятся в БД): `remaining` (amount − paid), `status` (Не оплачено / Частично оплачено / Оплачено).

#### Таблица `admin_users`

| Поле | Тип | Описание |
|------|-----|----------|
| id | uint, PK | Автоинкремент |
| username | string, UNIQUE | Логин администратора |
| password_hash | string, NOT NULL | bcrypt хеш пароля |

### API

```
POST   /api/auth/login                  # Авторизация → JWT

GET    /api/profiles?type=X&parent_id=Y # Список профилей
POST   /api/profiles                    # Создать профиль
GET    /api/profiles/:id                # Детали профиля
PUT    /api/profiles/:id                # Обновить профиль
DELETE /api/profiles/:id                # Удалить (каскад)

GET    /api/profiles/:id/orders         # Заказы профиля
POST   /api/profiles/:id/orders         # Создать заказ
PUT    /api/orders/:id                  # Обновить заказ
DELETE /api/orders/:id                  # Удалить заказ
PATCH  /api/orders/:id/pay             # Внести оплату
```
